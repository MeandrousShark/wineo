# 0033: Tags and `wineo list --tag`

## Goal

Let environments carry tags like `game`, `work`, or `creative`, and filter
`wineo list` by them, so a long list can be read in groups. This is GUI entry
criterion 7. The GUI will use tags for its sidebar groups or filters, so the
config shape settles here.

```toml
tags = ["game", "rpg"]
```

```
$ wineo list --tag game
007-first-light       exited    007              ended 2 days ago
Zomboid               stopped   project-zomboid  ended 2 days ago
palworld              inactive
```

## Existing foundation

- `wineo list` (`commands/list.rs`) has only `--json`. It calls
  `table::gather(paths, now, tz, |_, _| true)`, so a filter predicate already
  has a place to go. Rows are name, state, target, and time with no header.
  The JSON is `{ environments: [StatusOutput], errors }`.
- `status` with no name shows only running or busy environments, so it isn't
  a second list to filter.
- `targets.<name>.args` and `gamescope.args` are arrays of strings, set with
  `parse_args_value` in `edit.rs`: `wineo set NAME 'key=["a", "b"]'`.
- `name::is_valid` limits environment and target names to ASCII letters,
  digits, `-`, and `_`. The picker's `name_problem` turns a bad name into
  "Invalid input: spaces not allowed."
- Clone, snapshots, trash, and portable copies copy the config text as is, so
  a new top-level key travels with them for free. Templates are
  environment-shaped TOML, so `tags` works there once the struct has it.
- Completion has `environments()` and `targets()` completers; a tag completer
  would collect tags across every environment the same way.
- Adding the key needs no schema bump, the same as `kind` and `mangohud`: an
  older wineo refuses the config with `unknown field`.
- The maintainer has 16 environments, a mix of games and tests like
  `notepad` and `test`.

## Decisions for the maintainer

### 1. What a tag can be

**Recommended:** the same characters as environment names (ASCII letters,
digits, `-`, `_`), matched exactly, with duplicates refused. It keeps tags
easy to type and complete, and reuses `name::is_valid` and its error.

```
$ wineo set palworld 'tags=["co op"]'
Invalid tag "co op": spaces not allowed.
```

The alternative is lowercasing on write so `Game` and `game` can't both
exist.

### 2. How tags are edited

**Recommended: A, `set` only, for now.**

A. Through `set`, like any array:

```sh
wineo set palworld 'tags=["game", "co-op"]'
wineo set palworld --unset tags
```

B. `set` plus a small `wineo tag` command for adding and removing one tag
   without retyping the list:

```sh
wineo tag palworld add co-op
wineo tag palworld rm co-op
```

B is nicer to type, but it's a new top-level command. It can be added later
without changing the config.

### 3. Several `--tag` flags

**Recommended: all of them (AND),** like `gh issue list --label`. Each flag
narrows the list.

```
wineo list --tag game --tag co-op    # games that are also co-op
```

The alternative is any of them (OR), which reads as "show these groups
together."

### 4. Showing tags

**Recommended:** a `tags` line in `status NAME`, and `tags` in the JSON of
`list` and `status`. `list` gets no new column, since most rows would have an
empty one and the table is already wide.

```
$ wineo status palworld
palworld: inactive
  target     palworld (...)
  runner     ...
  tags       game, co-op
```

The alternative is a fifth `list` column.

### 5. When nothing matches

**Recommended:** a one-line note, exit status 0, like `status` printing
"Nothing is running":

```
$ wineo list --tag rpg
No environments are tagged rpg
```

With `--json`, an empty `environments` array and no note.

### 6. Where the key lives

**Recommended:** environments and templates, on both Wine and native
environments. No global or target-level tags, and nothing adds tags on its
own (Heroic import, native games, and `new` leave them empty).

## Completion

`--tag` completes tag values collected from every environment, deduplicated
and sorted, like environment names.

## Implementation sequence

1. Core: `tags` on the environment and templates, validation at load,
   `set`/`--unset`, and a helper that collects every tag.
2. CLI: `list --tag`, the empty note, `status` and JSON output, and the
   completer.
3. Docs: `config-files.md`, a short section in the README or its own page,
   `json-output.md`, `features.md`, and both example configs.

## Verification and acceptance

- Unit tests for parsing, bad characters, duplicates, templates, and
  `set`/`--unset` preserving comments.
- CLI tests: `list --tag` with one tag, several tags, no match, `--json`, a
  broken environment still reported under `errors`, and tag completion.
- The maintainer tags a few real environments and filters them.
- `cargo fmt`, `cargo clippy --all-targets -- -D warnings`, and `cargo test`.

## Scope limits

- No `--tag` on `status`, `start`, or other commands.
- No tag colors, descriptions, or hierarchy.
- No automatic tags.
